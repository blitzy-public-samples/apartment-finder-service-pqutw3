# Decision Log

This log is the single source of truth for **why** the security remediation was
implemented the way it was. Rule 1 (Explainability) forbids rationale in code
comments, so every judgement call that a competent engineer could reasonably have
made differently is recorded here instead.

**How to read this log.** Each row names a decision, the alternatives that were
genuinely available, the reason the choice was made, and the risk the choice
carries. Code comments in this repository state only *what* a construct is and
*what it does*; anything explaining *why one approach was preferred over another*
belongs in this file. Where a decision departs from a literal reading of the
Agent Action Plan (AAP) or of a user-specified Rule, it appears in
[Section 11](#11-deviations-from-a-literal-reading-of-the-requirements).

The finding identifiers in a section heading are those of the review that first
prompted that section's rows. Identifiers are per-review and are not comparable
across reviews, so rows added by a later review cite row numbers from this log
rather than a finding identifier.

Companion documents: `docs/security/TRACEABILITY_MATRIX.md` maps findings to
fixes and tests; `docs/security/RESIDUAL_RISK.md` records the accepted advisories;
`docs/security/CREDENTIAL_ROTATION.md` is the rotation runbook;
`docs/review/CRITICAL_DECISIONS.md` is the reviewer-facing summary of the five
highest-risk decisions.

## 1. Dependency and runtime decisions

| # | Decision | Alternatives considered | Rationale | Risks |
|---|----------|------------------------|-----------|-------|
| 1.1 | Replace `python-jose` with `PyJWT[crypto]` | (a) Keep `python-jose` and pin its transitive `ecdsa`; (b) adopt a heavier JOSE/key-set library | `python-jose` hard-requires `ecdsa`, whose CVE-2024-23342 (CVSS 7.4) has **no patched release and no planned fix** — the maintainers place side-channel resistance out of scope because it is unachievable in pure Python. No pin resolves it, so removal is the only remediation. `PyJWT` adds only `typing_extensions`, so the graph shrinks rather than trading one transitive set for another. | The exception hierarchy differs, so one `except` clause changed. Mitigated by tests asserting rejection of `alg:none`, algorithm confusion, wrong key, wrong audience/issuer and every missing required claim. |
| 1.2 | Replace `passlib` with `bcrypt` called directly | (a) Patch `passlib` in place as one community contributor published; (b) stay on `passlib` and pin an older `bcrypt` | `passlib` 1.7.4 (last release 2020) reads `bcrypt.__about__.__version__`, removed in `bcrypt` 4.0+, so `CryptContext.hash()` **raises** rather than degrading — password hashing is non-functional, not merely unmaintained. Patching in place forks an unmaintained dependency and must be re-applied on every install. Pinning an old `bcrypt` freezes a security-critical primitive. | `bcrypt` raises `ValueError` above 72 bytes where `passlib` truncated silently. Mitigated by an explicit schema-level byte ceiling that yields a 422, verified by test. |

The database work in the same coroutine stays on the loop — see row 12.7. |

## 2. Signing-key strength and secure defaults (F14, F20)

| # | Decision | Alternatives considered | Rationale | Risks |
|---|----------|------------------------|-----------|-------|
| 2.1 | Enforce a **per-algorithm** key floor (HS256 ≥ 32, HS384 ≥ 48, HS512 ≥ 64 bytes) driven by the strongest configured algorithm | Keep one flat 32-byte floor for all three algorithms | RFC 7518 §3.2 requires a key at least as long as the hash output. A flat 32-byte floor leaves HS384 and HS512 under-keyed, which is what the finding reported. Deriving the floor from the strongest configured algorithm means a deployment cannot weaken itself by widening the allowlist. | A deployment already running HS512 with a 32-byte key now fails at startup. This is intentional and loud rather than silent; the failure message names the exact byte count required. |
| 2.2 | Reject low-entropy signing keys by structure (distinct-character count, repeated runs, sequential runs) | Accept any value meeting the byte floor; or require a full entropy estimate | The finding showed a repetitive key such as `"Ab" * 16` passing the byte floor while carrying almost no entropy, and the template advertised a "5 distinct characters" rule the runtime never enforced. Structural checks are deterministic, explainable in a failure message and cheap. A full entropy estimator would be opaque and would reject legitimate random keys at the margins. | A randomly generated key could in principle trip a structural check. Probability is negligible at the enforced sizes, and the failure names the specific rule. |
| 2.3 | Rewrite `.env.example` to state **only** what the validators enforce | Leave the template's stronger-sounding claims in place | A template that promises a rule the runtime does not apply is worse than one that promises nothing: it creates false assurance. The template now names the per-algorithm byte sizes and the exact structural rules. | None identified. |
| 2.4 | Add dedicated, environment-validated HTTPS callback settings (`PAYPAL_RETURN_URL`, `PAYPAL_CANCEL_URL`) | Keep deriving the payer return/cancel address from the first entry of `ALLOWED_ORIGINS` | The CORS origin list answers a different question (who may call the API) from the payer redirect (where PayPal sends the user). Reusing the first origin coupled two unrelated settings and allowed a production deployment to retain an `http://` or `localhost` callback. Dedicated settings are validated to require HTTPS and a non-local host outside the local environment. Each is also refused if it carries a wildcard, fragment or user information, and the cancel address is refused if it equals the return address, so an approving payer and one who abandoned the checkout always land on different addresses. A query string is carried rather than refused, because `frontend/src/app.tsx` declares exactly one subscription route, `/subscription`, and no catch-all: both addresses must therefore name that one path and be distinguished by their query string, or one outcome would return the payer to a route the read-only frontend does not declare. | Two new required settings per environment. Both carry documented local-development defaults addressing `/subscription` with `?paypal=return` and `?paypal=cancel`, and a misconfiguration fails loudly at startup rather than silently redirecting payers. A deployment that configured one address for both outcomes now fails at startup. |
| 2.5 | Refuse `memory://` rate-limit storage outside the local environment | Allow it everywhere and document the limitation | Process-local counters are per-pod, so a limit of *N* becomes *N × pods* — the throttle silently weakens exactly as the deployment scales. Refusing the value at startup converts a silent weakness into a configuration error. | Non-local deployments must provision shared storage. Documented in `.env.example`. |

## 3. Token hardening (F9)

| # | Decision | Alternatives considered | Rationale | Risks |
|---|----------|------------------------|-----------|-------|
| 3.1 | Freeze the effective algorithm list into an immutable tuple resolved once at import | Read `settings.JWT_ALGORITHMS` at each verification | A list read per call can be mutated after startup — by a test, a plugin or any code holding the settings object — which would move a security-critical parameter outside the validated startup gate. A tuple captured at import cannot be changed by assignment to the settings field. | The process must restart to change algorithms. That is the intended property for a security-critical parameter. |
| 3.2 | Bound `create_access_token`'s `expires_delta` by the configured maximum, and reject non-positive values | Ignore the parameter; or clamp silently to the maximum | An unbounded override lets any caller mint a token outliving the configured ceiling, defeating the bounded-lifetime requirement. ## 4. Authorization (F18, F10, F19)

| # | Decision | Alternatives considered | Rationale | Risks |
|---|----------|------------------------|-----------|-------|
| 4.1 | Resolve an unknown, missing, blank or malformed role to an explicit **no-role** sentinel and refuse before any rank comparison | Map an unrecognised value to `GUEST`, the lowest role | Mapping to the lowest role is not deny-by-default: a route whose minimum *is* `GUEST` would then be satisfied by a corrupt or unrecognised value. The AAP requires that such a value "satisfies no minimum". Refusing before the comparison means no ordering accident can admit it. | A row with a legitimately new role name is refused until the enum is extended. That is the intended failure direction. |
| 4.2 | Carry the token's role claim as **non-authoritative** metadata and log claimed-vs-effective on every refusal; decide only from the database row | Decide from the claim (cheaper, no row needed); or discard the claim entirely | OWASP API Security is explicit that a service must not trust a role asserted by the client, so the claim can never decide. But discarding it loses the audit signal the AAP asks for — a claimed/effective mismatch is exactly the evidence of an escalation attempt. Carrying it for logging only satisfies both. | A reader could mistake the logged claim for the decision input. Mitigated by naming it `claimed_role` alongside `effective_role` in every record. |
| 4.3 | Make the ownership helpers return one indistinguishable `404` for both a missing row and a foreign row | Keep `404` for missing and `403` for foreign; or delete the helpers as unused | Distinct statuses are an existence oracle: a caller learns that an identifier it does not own nevertheless exists. Deleting the helpers was rejected because the AAP mandates an ownership helper as part of the centralized module. | A genuine "not found" is indistinguishable from "not yours", which is marginally less informative for legitimate clients. That is the intended trade. |
| 4.4 | Leave `filters.py` ownership predicates byte-identical | Route them through the new ownership helper for consistency | The AAP freezes these two expressions as already-correct untouchable interfaces. Rewriting correct code to look uniform is churn with no security gain and measurable regression risk. Verified: `git diff` for the file is empty. | The codebase has two ownership idioms. Accepted deliberately. |

## 5. Credential endpoints (F6, F7)

| # | Decision | Alternatives considered | Rationale | Risks |
|---|----------|------------------------|-----------|-------|
| 5.1 | Increment failed-attempt counters with a single conditional `UPDATE` whose arithmetic the database performs | Read-modify-write in Python; or serialize with an application lock | Read-modify-write loses increments under concurrency: two parallel requests both read *n* and both write *n+1*, so an attacker gains attempts by parallelising. Computing the new value inside the statement makes it atomic without any lock. Proved on SQLite before adoption. | Semantics now live in SQL rather than Python, which is less obvious to a reader. Covered by a test in which two independent sessions both record a failure and the stored count reaches 2. |
| 5.2 | Normalize total hashing work across the unknown-account, locked-account and wrong-password paths, and pad to a measured floor | Short-circuit when the account is absent (the reported defect); or add a fixed sleep | Short-circuiting leaks account existence through timing. A fixed sleep does not adapt to the configured bcrypt cost, and a *legacy* hash with a lower embedded cost still finishes early — the specific oracle the finding described. One comparison against the stored-or-stand-in hash plus one fixed-cost decoy comparison, padded to a floor measured at import, makes all three paths equal. Measured: legacy/absent ratio fell from 266,000,000× to a 0.0% spread. | Every login now costs at least two bcrypt comparisons; suite runtime rose from ~7s to ~30s. Accepted as the cost of closing the oracle. |
| 5.3 | Remove `verify_decoy` | Keep it for symmetry | It was both unreferenced and itself the un-normalized comparison the finding describes; leaving it invited reintroduction of the defect. | None — no caller existed. |

## 6. Payment lifecycle (F1–F5, F20)

| # | Decision | Alternatives considered | Rationale | Risks |
|---|----------|------------------------|-----------|-------|
| 6.1 | Perform capture inside the **verified webhook** rather than adding a capture route | Add `POST /subscriptions/capture` for the client to call after approval | The AAP freezes the route inventory at nine; a capture route would be a tenth. The webhook is already authenticated by signature, already owner-resolvable from the stored order id, and already the transactional boundary — so it is the natural place. | Capture depends on webhook delivery. Mitigated by idempotent activation keyed on the capture id, so a later delivery or replay settles the row exactly once. |
| 6.2 | Commit the pending subscription row **and** its idempotency key before the external PayPal call | Call PayPal first and persist the result | If the external call precedes the commit, a crash between them leaves money moved with no local record, and a retry opens a second order for the same intent. Persisting first means every order is traceable to a row, and re-sending the same `PayPal-Request-Id` reuses the original order. | A pending row can outlive an abandoned checkout. Harmless: `GET` filters on active status and a future end date, so a pending row grants nothing. |
| 6.3 | Require capture status `COMPLETED` **and** an exact amount+currency match against the server plan catalog before activation | Trust the capture response; or check the amount only | The catalog is the only price authority. Comparing amounts as two-place strings avoids float equality problems, and checking the currency prevents a same-numeral different-currency settlement from activating a plan. | A legitimate capture whose representation differs (for example trailing-zero formatting) would be refused. Normalisation to two places is applied to both sides before comparison. |
| 6.4 | Verify the webhook signature against the **exact raw request bytes** | Verify against `request.json()` re-serialized | Re-serializing changes key order and whitespace, so the verifier no longer sees what PayPal signed and verification becomes meaningless while still appearing to succeed. The raw body is retained and spliced into the postback verbatim, and no business field is parsed until verification passes. | The handler holds the raw body in memory. Bounded by the request-body-size cap. |
| 6.5 | Validate the certificate host against an allowlist **before** the URL is used or forwarded | Fetch or forward whatever the header names | `PAYPAL-CERT-URL` arrives in an attacker-controllable request header. An unrestricted verifier can be pointed at an attacker-hosted certificate and made to accept a forged payload — so verification without the allowlist offers false assurance rather than assurance. | An allowlist must be maintained if PayPal changes certificate hosts. Configuration-driven, not hardcoded. Eight off-allowlist URLs are tested, each asserting no outbound request is made at all. |
| 6.6 | Acknowledge an already-processed delivery with **200 and no state change** | Return 409 Conflict (the reported behaviour) | PayPal retries on any non-2xx, so answering a duplicate with 409 converts normal at-least-once delivery into a retry storm — a self-inflicted availability problem. A 200 with no mutation is the correct at-least-once acknowledgement. | A genuine duplicate is indistinguishable from success in the response. The distinction is recorded in the log and in the delivery table. |
| 6.7 | Remove `amount`, `start_date` and `end_date` from the subscription request contract entirely | Keep the fields and validate them server-side | Validating a field a client should not influence still leaves it in the contract and one refactor away from being trusted. Absence makes tampering structurally impossible. Verified zero-impact: no frontend caller sends them. | A client sending the old fields now receives a validation error rather than silent ignoring. Intended, and no such client exists. |
| 6.8 | Never grant or alter the `ADMIN` role through payment lifecycle events | Let role promotion use one common code path | Payment is an entitlement signal, not an administrative one. Excluding `ADMIN` from both the promote and revoke paths means no purchase, refund or reversal can touch administrative privilege. | Slightly more code than a single generic path. Accepted for the guarantee. |
| 6.9 | Move every PayPal call to a pooled per-event-loop `httpx.AsyncClient` | Keep synchronous `httpx` calls inside the async handlers | A blocking call inside an async route stalls the whole event loop, so the anonymous webhook becomes a denial-of-service lever. Pooling bounds concurrency and reuses connections. | Client lifecycle must be managed; a `lifespan` handler disposes the pool. Verified: no synchronous `httpx` call remains and the pool is reused. |
| 6.10 | Guard the token cache with a brief `threading.Lock` rather than an `asyncio.Lock` | Use `asyncio.Lock` | On Python 3.9 an `asyncio.Lock` created at import binds to whatever loop is current then, which breaks across loops (notably under the test client). The lock is held only around a synchronous read/write of the cached value and never across an `await`. The separate single-flight refresh lock, which *is* awaited, remains an `asyncio.Lock` and is bound per loop instead — see row 6.18. | A reader must confirm the lock is never held across an await. That property is maintained deliberately. |
| 6.11 | Ask PayPal for a complete representation on capture, and read the order back only when the response still carries no capture object | (a) Trust the capture response exactly as returned; (b) fetch the order after every capture unconditionally | PayPal may answer a capture with a minimal body carrying an identifier and a status and nothing else. The measurement step then finds no amount and no currency to compare against the plan catalog and refuses the settlement — so a payer who had already been charged received a failure. Requesting the full representation makes the complete body the normal case, and reading the order back only when the capture object is still absent keeps the extra round trip off the common path. | One additional provider call on the minimal-body path. Covered by tests asserting the header is sent, that a minimal body costs exactly one read-back and settles, and that a complete body costs none. |
| 6.12 | Withdraw `POST /subscriptions/capture` and its request model, so the service accepts no provider identifier from any client | (a) Keep the route and bind it to the authenticated owner; (b) keep it for a client that cannot receive webhooks | Row 6.1 records that capture belongs in the verified webhook, yet the route existed and took a provider order identifier from the request body. Keeping it — even owner-bound — leaves a client-supplied identifier as an input to a money-moving path and takes the route inventory to ten, which the AAP freezes at nine. With it withdrawn, every order identifier in the system was minted by this service's own create-order call. | Settlement depends entirely on webhook delivery. Mitigated by activation keyed on the capture identifier, so a delayed or repeated delivery settles the row exactly once, and by the settled-order recovery path. |
| 6.13 | Activate from the complete capture outcome, including on the settled-order recovery path | Rebuild the outcome from a reduced identifier-and-status envelope; or refuse a settled order the capture call could not report | The recovery path reduced the verified outcome to an identifier and a status, after which the measurement step had no amount or currency to compare against the catalog — so recovery failed deterministically for exactly the settled orders it existed to rescue. Passing the outcome through unchanged preserves the amount, currency and capture identifier the comparison needs. | The outcome type is part of the internal contract between the service and the endpoint. Covered by tests that recover a settled order and that refuse one settled below the plan price. |
| 6.14 | Reuse the most recent open intent for an account and plan, and never clear a provider order identifier once it is stored | Insert a new row and a new idempotency key on every create; or refuse a second create while one is open | A new row per attempt left an unbounded trail of pending rows, and a new idempotency key each time made PayPal open a fresh order for the same intent. Clearing the order identifier when an attempt failed orphaned an order that may already have been paid, leaving nothing to reconcile against. Reusing the open attempt with its original key makes PayPal return the original order, and retaining the identifier keeps every order traceable to a row. | An abandoned checkout is re-driven rather than replaced. Harmless: a pending row grants no entitlement, because retrieval filters on active status with a future end date. |
| 6.15 | Answer a persistence failure after the provider was engaged with `503` and a reconciliation detail, and one before it with `400` | Answer `500` for both; or answer `400` for both | The two failures are operationally different. Before the provider is called nothing has moved and the request can simply be refused. After it, an order exists and may have been paid, so the caller must be told the state is unresolved rather than that its request was bad. The webhook's final commit was previously unguarded and would have surfaced as a `500`, which says nothing about reconcilability. | A client receives a `503` it cannot retry into success. Intended: the row and the order identifier are both recorded, so reconciliation is server-side. |
| 6.16 | Let no function in the PayPal service touch the caller's transaction | Keep the rollbacks inside the capture and settled-order calls; or have the webhook re-insert its replay claim afterwards | The webhook flushes its replay claim inside the request transaction so a concurrent duplicate delivery is rejected by the uniqueness constraint. A rollback inside the provider call discarded that claim, so exactly-once processing was lost precisely when two deliveries raced. Re-inserting afterwards reopens the window the claim exists to close. | The webhook holds its database connection for the duration of the capture call. Accepted deliberately as the price of an atomic exactly-once claim; the outbound call carries an explicit timeout and the connection pool is bounded. |
| 6.17 | End the create-subscription transaction before the provider call and re-read the row afterwards | Keep the refresh before the call; or hold the transaction open across it | Sessions expire on commit, so reading any attribute after the commit reopened a transaction and held a pooled connection for the whole external timeout — a handful of concurrent creates could exhaust the pool while every one of them was merely waiting on PayPal. Copying the two values the call needs before committing, touching no attribute between the commit and the await, and re-reading the row afterwards keeps the connection out of the provider's latency entirely. | The row is read twice per create. Covered by a test asserting no transaction is open while the provider is called. |
| 6.18 | Bind the pooled client and the single-flight refresh lock to the loop that created them, comparing loops by object identity | One process-wide client plus a dictionary of locks keyed by `id(loop)` | An `httpx.AsyncClient` and an `asyncio.Lock` each belong to one loop, and handing either to another loop is undefined. `id(loop)` is worse than useless as a key: a collected loop's address can be reused by a new object, so a stale entry can be mistaken for a live one. Comparing the loop object itself cannot alias, and at most one client and one lock exist at a time, so a loop that has ended leaves nothing behind. Extends row 6.9. | A call issued on a loop other than the one that opened the pool builds a temporary client and loses pooling for that call. Covered by a test asserting the shared client is never handed to another loop. |
| 6.19 | Hold a failed credential exchange back for a fixed window without making any caller wait | Leave the advertised backoff unimplemented; or make callers wait for the window to elapse | The module documented a bounded wait and a failure backoff that no code read — the constants had no reader and one had no module-level definition — so the contract was false and every caller re-attempted immediately, hammering a failing provider. Recording the deadline and the failing category, and answering subsequent callers from that record without sending a request, throttles the provider without ever blocking a caller; a wait would convert a provider outage into a queue of stalled requests. The unimplemented wait constant was removed from the constants, the export list and the docstring rather than left advertised. | A caller inside the window receives the recorded failure rather than a fresh attempt. Bounded by the backoff constant and cleared by a successful exchange or a cache reset. |

## 7. Application surface, body cap and logging (F8, F11, F12)

| # | Decision | Alternatives considered | Rationale | Risks |
|---|----------|------------------------|-----------|-------|
| 7.1 | Disable `/docs`, `/redoc` and `/openapi.json` outside the local environment | Leave them public; or gate them behind admin authorization | The schema enumerates every route, parameter and model to an anonymous caller, which is outside the authorized anonymous surface. Passing `None` for the three paths also removes `/docs/oauth2-redirect`, which an admin gate would have left mounted. | Non-local environments lose interactive docs. The schema remains generatable from the code. |
| 7.2 | Replace the list + `pop(0)` body replay with a `deque` and `popleft`, and bound the message count | Keep the list; or buffer the whole body as one object | `pop(0)` is O(n) per chunk, so replaying *n* chunks is O(n²) — a many-small-chunks request becomes a CPU amplifier. A `deque` makes each pop O(1), and a message-count bound stops an unbounded stream of empty chunks that no byte-size cap would catch. | One more configured limit. Defaulted and documented; tested by driving the middleware with 65 explicit ASGI messages against a cap of 8. |
| 7.3 | Log an exception class plus a correlation id instead of a traceback, and set SQLAlchemy `hide_parameters=True` | Keep `exc_info`; or scrub log text after the fact | A traceback frame can carry bound statement parameters — an email address, a street address, a name — so the log becomes a PII sink. `hide_parameters` removes them at the source, which is more reliable than pattern-scrubbing output. A correlation id preserves the ability to tie a client-visible error to its log record without carrying the payload. | Less immediate detail when debugging. The correlation id and exception class remain, and parameters can be re-enabled deliberately in a non-production environment. |
| 7.4 | Read the listener's running state from the saved reference, drain while it is still installed, then release it and stop the thread | (a) Release the reference first and then test it, which is what the code did; (b) stop the thread first and drain afterwards | The running test read the module reference the same function had just cleared, so it always answered "not running": the queue was never drained and `stop()` was never called. Every replacement left a live thread behind, and every record still queued at exit was lost. The drain has to run before the stop because it is what waits for the already-queued records, and it needs the reference still installed because the drain itself tests for a running listener. | `QueueListener.stop()` joins its monitor thread with no timeout and is reachable for the first time. The bounded drain runs first, so by the time the sentinel is enqueued the queue is empty or the wait has elapsed. |
| 7.5 | Report an incomplete shutdown drain as a fallback record on standard error | Expose it through a health or shutdown status; or continue discarding the result | The lifespan called the drain and discarded its result, so records lost at shutdown were lost silently. A health surface is not reachable at the moment a process is stopping, whereas the fallback writer reaches standard error directly — the one path that does not travel through the queue that has just failed to empty. The record carries the drain timeout, so an operator can distinguish a slow drain from a stuck one. | The report appears in the process's own error stream rather than in the structured log stream. That is the property being relied on. |
| 7.6 | Do not stop the listener from the application lifespan | Stop it there, for symmetry with the outbound client shutdown | The queue handler falls back to writing inline only when the queue is *full*, so a stopped listener silently strands every record emitted after the lifespan exits — server teardown and interpreter-exit hooks included. Draining in the lifespan and stopping at interpreter exit keeps every record on a path that writes it. | The listener outlives the lifespan by design. ### 10.17 The boundary applied between rationale and behavioural documentation

Rule 1 forbids *rationale* in code comments; the AAP separately requires
(CQ2) that public APIs and non-obvious logic be documented. Those two
obligations meet at a boundary, and the following test was applied uniformly so
that the result is reviewable rather than a matter of taste.

A comment or docstring **may** state:

* what a construct is, and what it does;
* the value or behaviour it produces, including a contrast that is itself
  behaviour — for example "returns `False` rather than raising when the stored
  hash cannot be parsed", which is the function's contract;
* the resulting order, status or shape a caller can rely on.

A comment or docstring **may not** state:

* why one approach was preferred over another that was available;
* what alternative was rejected, or what would have happened otherwise;
* the threat or risk being mitigated;
* an invariant framed as a justification, such as "Ordering invariant: … so …".

Two consequences of applying this test are recorded because they are judgement
calls a reviewer could reasonably have made differently:

1. **`.env.example` retains its explanatory prose.** Rule 1's prohibition is
   directed at *code comments*. A configuration template is operator-facing
   documentation whose purpose is to let a human configure the system correctly,
   and F14's own resolution required that template to state accurately what the
   validators enforce. Stripping the standards citation behind the key-size
   floor, or the reason a wildcard host is refused, would degrade a deliverable
   another finding required. The prose was therefore left in place.
2. **Behavioural contrasts were left in place throughout.** A phrase such as
   "the clear is one `UPDATE` on the row rather than a read followed by a write"
   documents what the code does, not why that was chosen; the *why* for that
   same decision is row 5.1 of this log. Only clauses that justified, weighed or
   warned were removed.

Hashing the exact inline script of the response being sent restricts inline execution to the byte sequence the application itself generated, where `unsafe-inline` would admit any script injected into the same page. Relaxing the global policy would weaken every API response for the benefit of two HTML pages. Withdrawing the routes contradicts row 7.1, which publishes them locally on purpose, and the application-surface test that asserts them. Vendoring the viewer assets is new functionality and a supply-chain change of its own. A nonce needs a per-response random value and the same page rewrite, with no advantage over a hash for a body the application generates deterministically. | The digest is recomputed per response, so a viewer upgrade that changes the inline bootstrap needs no code change — but one that changes *where* the viewer fetches from does, because each permitted origin is named explicitly. Every named origin is a supply-chain trust decision, pinned to the versions the framework requests. A developer with browser tooling attached still sees one refused source-map fetch, recorded as row 12.8. |

## 14. Runtime QA findings — request correlation, webhook body type, ingestion isolation

Rows added for the QA testing round whose findings were numbered FINDING-1 to
FINDING-7 against the provider and observability runtime. That numbering is
per-review, so these rows cite behaviour rather than an identifier.

| # | Decision | Alternatives considered | Rationale | Risks |
|---|----------|------------------------|-----------|-------|
| 14.1 | Attach the bound request identifier in `QueueDispatchHandler.prepare`, keeping the existing attachment in `RedactingFilter` as well | (a) Add the redacting filter to the queue handler as well as to the stream handler; (b) capture the identifier into the record at every call site; (c) drop the queue and emit synchronously | The identifier lives in a `contextvars` variable, which is per task and per thread. The only code that read it ran inside the filter installed on the *listener-side* stream handler, so it executed on the `QueueListener` thread and always read `None` — no record on the normal path carried a `request_id`, and correlation appeared only during queue overflow, which is worse than absent because it looks like it works. `prepare` is the last step that runs on the thread that logged, so reading it there is the smallest change that makes every path correct. Adding the whole redacting filter to the queue handler would have moved redaction, formatting and serialisation back onto the request path, which is exactly what the queue exists to prevent. Per-call-site capture would have to be repeated forever and would be forgotten once. | `prepare` no longer returns the record untouched. It sets one attribute and never raises, and the inline overflow path is covered because `emit` prepares before it enqueues. |
| 14.2 | Redact registered secret values literally, in addition to matching credential shapes | (a) Accept that a credential quoted in free prose survives; (b) read the configured secrets inside the logging module; (c) hash or fingerprint values instead of holding them | Shape matching needs a credential-shaped key name beside the value, so a provider that quotes a key inside an error sentence defeats it — measured with a provider error body reading `bad key <value> rejected`. A literal pass closes that. The logging module must not read configuration: it is imported from exception handlers and must stay leaf-level and cycle-free, which is why each module that *handles* a credential registers it instead. Fingerprinting cannot rewrite the value in text that already contains it. | Over-redaction if a registered value also occurs innocently. Bounded by an eight-character floor, a thirty-two value ceiling, and by registering only provider credentials. A value changed after import is not covered, so the registry is a safety net rather than the primary control. |
| 14.3 | Register the provider credentials from the three service modules that handle them, and not the signing key or the database URL | Register every secret setting from one place — the settings module or the application entrypoint | The settings module is deliberately leaf-level so that nothing it imports can cycle back into it, and the logging module reads no configuration; a single registration point would have to violate one of those two properties. Registering in the module that already holds the credential keeps both intact. The signing key and the database URL are handled elsewhere and their realistic leak shapes — an `Authorization` header, a `secret`-named field, a `postgresql://user:pw@` URL — are already matched by shape. | Four values are registered rather than six. A future credential must register itself; the module that introduces one is the module that would. |
| 14.4 | Normalise the raw notification body once inside `verify_webhook_signature` | (a) Encode inside the postback builder; (b) remove the text branch from `webhook_body_object` so a text body is rejected | The two functions disagreed about the accepted type: one decoded text happily while the other raised `TypeError` on it, so a caller holding text got an exception from a function whose contract is that every failed check is *returned*. Normalising once means the bytes that are decoded are the bytes that are transmitted, which is the property the signature check depends on. Encoding inside the builder would have left the two functions still deciding the type separately; rejecting text would have made the tolerant function's own contract a lie. | A caller passing text now has it encoded as UTF-8. If that caller had decoded the request with another codec the re-encoded bytes would differ and PayPal would answer `FAILURE`, which is the correct outcome rather than a silent pass. |
| 14.5 | Write each provider record inside its own savepoint | (a) Keep one flush at the end of the pass; (b) de-duplicate identities in memory before writing; (c) open a fresh session per record | One flush at the end meant a single unwritable record discarded every other record in the payload — measured with a repeated address and with a NUL byte, each of which cost the whole pass — and it would keep costing every pass for as long as the provider returned that record. A savepoint per record also makes each write visible to the next record's identity lookup, so a repeated address is reconciled as a refresh, which is what the module's own premise says should happen; an in-memory de-duplication map would have handled that case only and left every other refusal fatal. A session per record would abandon the one-session, one-commit contract. | A 500-record payload now issues 500 savepoints and flushes rather than one batch. Measured at under one second for 500 records against real PostgreSQL. |
| 14.6 | Attribute only constraint, data and value-adaptation failures to the record; raise everything else | Isolate every exception the write raises | Isolating everything would turn a systemic failure — a revoked privilege, a dropped connection — into one refusal record per remaining record and a pass that still reported "Completed", which is a worse signal than the failure it replaced. A constraint violation, a value the column cannot hold, and a value the driver cannot adapt describe the record; a missing privilege describes the session. Verified by driving both: a real `CHECK` violation is counted and dropped while the pass commits, and a real `REVOKE INSERT, UPDATE` still ends the pass with rows unchanged and the pool released. | A failure class outside the three would end a pass that isolation could have survived. Preferred to the reverse, and the classification is a named constant rather than a scattered condition. |
| 14.7 | Report an ingestion failure by exception class and driver error class, carrying no message text | (a) Keep the driver message; (b) strip only the driver's `DETAIL` line; (c) redact the message by pattern | The module states that a failure record names how far the pass got and never a listing, and the driver message broke that: PostgreSQL's server-side `DETAIL` line repeats the value it refused, and `hide_parameters` does not suppress it. Stripping `DETAIL` alone is not enough, because a driver's *first* line also quotes values for some errors — `invalid input syntax for type … : "…"`. Pattern redaction cannot know which quoted fragments are provider data. The driver's error class — `UniqueViolation`, `CheckViolation`, `InsufficientPrivilege` — carries the diagnostic value without the data, so it is reported instead. | Less free text when debugging an ingestion failure. The exception class, its module, the driver error class and the progress counter remain, and the traceback is still available at `DEBUG`. |
| 14.8 | Name the failed contract fields on a discarded provider record | (a) Leave the discard record without context; (b) include the validation error message | A systematic discard was indistinguishable from any other: the record named no field, so an operator could not tell that, for example, every listing was being dropped for a date the contract cannot parse. The validation message would name the fields but is generated text and could carry a value in some cases, so the field names are taken from the error's locations and filtered against the contract's own declared field names — a closed set that cannot contain a provider value. | The record names which field failed. That is the intent; it is a contract field name, not provider data. |
| 14.9 | Refuse a listing address that is not an absolute `http`/`https` URL, and refuse NUL in either text field | (a) Leave the address bounded only by length; (b) also refuse other control characters; (c) sanitise the value instead of refusing it | The address field had a length ceiling and no shape, so `javascript:alert(1)` validated and was stored — and, measured through the admin write endpoint, answered `200`. A scheme allowlist with a host requirement and no user information refuses that class of value at the contract, which is where the other field bounds already live. NUL is refused because no text column can store it: the driver raised on it at write time, which cost the whole ingestion pass and answered `500` on the write endpoint; refusing it at the contract turns both into a named validation failure. Only NUL is refused, not every control character, because a provider address legitimately carries newlines and refusing those would drop valid records. Sanitising would store a value the provider never sent. | An address form outside the allowlist is now refused rather than stored. No client sends one: the write endpoint's own tests supply none, and the provider supplies web URLs. Free text in `street_address` is deliberately still stored as data. |
