Security Remediation

apartment-finder-service

Twenty security findings remediated in code across authentication, authorization, payments and secrets: fifteen proven by automated test, five carrying an operational step no test here can perform. No new product functionality. Deployment and credential rotation remain for an operator.

Prepared for executive leadership and the change-approval reviewers

Remediated in code is the honest verb, not closed. Every one of the twenty findings has its fix delivered and a test that proves it, but three kinds of work cannot be done from inside this repository: rotating the credentials that were exposed, mounting the provisioned secrets into the running pods, and provisioning the new deployment inputs. Those are the operator items, and the slide near the end of this deck lists them. The breaking change is that writing to the listings corpus now requires the administrator role.

Authentication

Cluster one of four

Identity

Sign-in can no longer be talked into trusting a stranger

  • Only approved signing methods are accepted.
  • A weak signing secret stops startup.
  • Sign-in no longer reveals who has an account.
  • Password checking repaired; nobody must reset.
Approved methods
Startup validation
Full claim checks
Passwords verify
The accepted signing methods are now a fixed allow-list held in validated configuration, so a deployment can no longer be configured to accept an unsigned token. A signing secret that is too short, or that matches the placeholder the old developer-setup script wrote, now fails startup instead of quietly issuing forgeable tokens. Sign-in used to answer differently for an unknown address than for a wrong password, which let an attacker enumerate accounts; both paths now do the same work and return the same answer, and repeated failures lock the account for a short window. Password hashing was not merely unmaintained, it had stopped working altogether; every password already on file still verifies, so no user is forced to reset.

These four roles are not new scope; they are the project's own documented design intent, specified in its requirements and never built. Before this work every protected route asked only whether the caller was signed in at all. Two design points matter. The check denies by default, so an absent, unrecognised or oddly cased role satisfies no minimum and the request is refused rather than allowed through. And the role is read from the account record loaded during sign-in, never from the token the caller presents, because a value the client supplies cannot be trusted to describe the client's own privileges. Exactly one administrator exists, created by a separate migration step that logs the grant and asserts the count, and no other code path can write that value.

Payments

Cluster three of four

Payments

The buyer can no longer name its own price

  • Price and period come from a server catalogue.
  • Client amount and date fields no longer exist.
  • Capture is bound to the paying account.
  • Hosted redirect kept: no card data here.
Server pricing
Bound capture
Verified notices
Repeats refused
The amount and the access dates were previously taken from the request body, so a buyer could name its own price and grant itself any length of access. Those fields are now absent from the contract rather than merely validated, which makes tampering structurally impossible: there is nothing to tamper with. Capture now resolves the order to its stored row and checks that the row belongs to the caller. Incoming payment notifications are cryptographically verified before anything is read from them, the certificate host is checked against an allow-list first because that address arrives in an attacker-controllable header, and a repeated notification is refused so each event is processed once. The hosted redirect is unchanged, so no card number ever enters this system.

This repository had no ignore rules at all, which is why committed credentials are treated as a critical rather than a high finding. A database connection string and a cloud service-account key were committed, and the signing key every developer environment used was a published placeholder. Separately, the listings-provider key travelled in web addresses and was printed into logs when a call failed. All are out of the code now and cannot return, but removal only stops future exposure: anything already exposed stays live until it is rotated, which is the operator step this deck returns to. Managed secret storage is provisioned, the service is authorized to read it, and the manifests that mount it into the running pods are versioned here too: a provider class names the six secrets and the pod mounts them read-only as files. What an operator supplies is each secret's value.

Supply chain

Three building blocks replaced, for three different reasons

  • Own flaws fixed; a bundled part has no fix.
  • All three replaced rather than upgraded.
Replacement reasons
ReplacedNow in useWhy it had to go
Token library Maintained token library Needs a component nobody will fix
Hashing wrapper Hashing library, called directly Unmaintained; had stopped working
Payment kit Direct provider calls Archived; cannot verify notifications
Overall 19 → 7 advisories Four closed by removal alone
The three reasons are genuinely different. An earlier version of this slide applied one reason to all three, which was wrong. The token library's own two published vulnerabilities were fixed by its maintainers; what has no fix is a cryptography component it requires, whose maintainers have stated publicly that the flaw is out of scope for their project and no fix is planned. So upgrading the token library would not have helped, and removing it was the only remediation. The hashing wrapper has no vulnerability at all: it was last released in 2020 and had stopped working against the current hashing library, so sign-in was broken. The payment kit is archived by its vendor and never implemented notification verification, so no version of it could deliver the control this work needed. Several advisories were also closed by removing or simply omitting a package rather than upgrading one.

On the breaking change: the impact was measured rather than estimated. No client in this repository calls that route, and the ingestion task writes to the database directly, so that workflow is untouched. It is stated in the readme, the review document and the decision log, never introduced silently, and it needs a sign-off. On the seven in the deployed service: each has a named compensating control, and two automated guards run on every change. The eighth sits in the test framework, which no deployed process installs, and that absence is its control. Be precise about what those guards prove. One asserts a package stays absent. The other has two layers, and the first layer is a text search that an aliased import or a dynamic call would evade, which is why a second layer parses the code and follows aliases. Together they detect the realistic ways an acceptance could lapse; they are not a proof that it cannot. On credentials: removal stops future exposure only. Rotation is the required next step, is irreversible, and is therefore sequenced last.
Before this can be released

Four things an operator must settle first

The code is remediated and tested. Four gates stand before a first release, and none can be settled from inside a commit.

Summary summary
GateWhat it needs, and what happens until then
The cluster's control plane is private, and the release now reaches it over an authorized path rather than a public one. Access is granted by permission, not by network location, so the deploying identity needs that permission granted. Until it is, no release path can reach the cluster at all — which was already true before this work, silently.
Images now publish to a newly defined registry, because the previous one stopped accepting them. The registry must be created and the release identity given write access to it. The release refuses to reuse a version label and verifies which image is actually running, so a release that changes nothing can no longer report success.
One small cloud function runs on a language version its platform no longer accepts for new or updated deployments. The version is a fixed constraint of this work and was not raised. That function is therefore left out of the deployment until an owner decides between raising the constraint and retiring the function. Everything else releases normally; this step reports itself blocked rather than failing the release or quietly weakening the constraint.
The release updates cluster objects it will not create, so a brand-new cluster needs one apply first. The definitions are versioned here and both release paths apply them, but each path first checks the two serving objects exist and stops naming whatever is missing. Nothing is created implicitly, so a misnamed target fails early instead of half-way through.
Cluster access by permission
New image registry
One function blocked
Applied state to confirm
These are the seven operator items counted on the metrics slide, grouped into four pieces of work, and none of them can be done from inside a commit. Rotation covers a database connection string, a cloud service-account key, a signing key and a partner API key; the runbook orders it revoke, rotate, delete, then review prior access, because rewriting history before revoking leaves a live credential in every existing clone. The Kubernetes manifests and the mount that delivers each secret are versioned here; what an operator supplies is each secret's value, and one apply of the workload group against a cluster that does not have the two serving objects yet. The deployment inputs include a renamed cluster-location secret, federated identity replacing a long-lived key that must be deleted rather than left unused, and a runner with a network path to the now-private control plane. The disclosure channel needs private reporting switched on and a mailbox someone is accountable for reading; until then the security policy publishes no address and commits to no response times, which it says plainly. Every item is listed in the decision log's reconciliation section.

Two clarifications a new developer needs. The example configuration file starts the local profile as it stands, but it does not carry a working default for everything: the listings provider, payment and email keys are non-functional placeholders, accepted only while the environment is local, and the cloud profile additionally needs a real database instance name. Startup refuses a weak or placeholder value rather than degrading quietly, so a missing setting fails loudly and names itself. On the pipeline: the dependency audit, the code scan, the full test suite, the security suite and both guards do gate every change, and the deployment workflow calls that same pipeline rather than repeating part of it. Two checks are not gated and must be run locally, the infrastructure validation and the container build. The frontend job is a limited gate rather than an exempt one: it lints the whole tree against a recorded warning budget and runs the unit tests, but no type check and no production build. It passes today, and a regression inside it fails the pipeline. An earlier version of this note said it was expected to fail and gated nothing.
