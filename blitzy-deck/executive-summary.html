Who the service believes you are

Sign-in can no longer be talked into trusting a stranger

  • Only approved signing methods are accepted; forged tokens are refused.
  • A weak signing secret stops startup rather than issuing tokens.
  • Sign-in no longer reveals whether an address has an account.
  • Password checking repaired; no user must reset.

Authorization

Cluster two of four

Realizing documented design intent

Four roles, one central decision, denied by default

  • These four roles are the project's own documented design intent.
  • One central check decides access and denies by default.
  • Roles come from the account record, not the browser.
  • Exactly one administrator exists, via a separate auditable step.
RoleWhat an account of this kind may do
GuestBrowse listings. No account required, and page sizes are now bounded.
RegisteredSave search filters and take out a subscription. Sees only its own records.
PremiumEverything a registered account may do, carrying a paid entitlement.
AdminEverything above, plus writing to the shared listings corpus. Held by one account.

What to decide

Residual risk, and what holds it in check

One deliberate breaking change: POST /listings/ now requires the administrator role.

RiskHow it is held in check
POST /listings/ is now restricted to the administrator role. Deliberate, and the one breaking change in this release. Impact was measured, not estimated: no browser client calls it, and the listing ingestion service writes straight to the database, so that workflow is unaffected. Stated in the project readme and in the review document, never introduced silently.
Seven dependency advisories are accepted as residual risk. No fix for any of them is installable on the runtime this service deliberately pins. Each one carries a named compensating control, and an automated pipeline guard fails the build if a control ever stops holding, so the acceptance cannot lapse quietly.
The credentials that were exposed stay live until they are rotated. An ordered rotation runbook is delivered with the change. Rotation is the required next step and is sequenced last, because it cannot be reversed.
New required settings must be present before the service will start. Startup refuses a weak or placeholder value by design rather than degrading quietly, and every setting ships documented with a safe local default.
